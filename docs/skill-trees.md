# Three Skill Trees and a Revenue Layer for Self-Learning LLM Agents

A master of code, a master of graphics, a master of understanding, and the business skills that connect them to income. Every skill explains why it exists, how it is made, what can be changed, how it is learned, how mastery is shown, and where the sources are.

* **Agent 1. Code Master (logic):** 36 skills on a ladder of five tiers. Write, read, edit, delete, debug and ship any code, learn any language, and specialise.
* **Agent 2. Graphics Master (imagination):** 36 skills in an imagination core plus six rings, from the smallest pixel to 3D, motion, AI and media not yet invented.
* **Agent 3. Understanding Master (logic and imagination):** 36 skills on a helix of seven rungs: quantum physics, dark matter, life, learning any language or field, and communication.
* **Revenue Layer (shared by all agents):** 16 master-level skills in five stages: find demand, win customers, deliver, get paid lawfully, and stay safe.

124 skill cards, evidence-graded. Clickable source links on every card, full bibliography at the end. Prepared October 2026.

### Four points that are easy to get wrong

1. **'Unlimited' is a direction, not a property.** The trees raise the ceiling and give a method for entering anything new (L-31, G-36, U-30), but no document makes a model able to do everything. Each skill states its limits.
2. **Heavy science needs honesty about the unknown.** Quantum interpretations, dark matter, dark energy and the origin of life are open or contested. Agent 3 is built to label what is established, supported, speculative or unknown, with dates (U-35).
3. **The revenue layer does not promise income.** Most online ventures earn little or nothing, and platforms ban some automation. The layer teaches how to find real demand, deliver checked work and stay lawful, with human approval on money (R-16).
4. **The trees are files, not code.** They are meant to live in an ICM workspace (Jake Van Clief): plain-text folders, one skill card per stage, and a human who can edit any stage file (Appendix B).

### Where to start

* **Agent 1:** L-01 to L-07, then L-31 and L-32.
* **Agent 2:** G-01 to G-03, then Ring 1.
* **Agent 3:** U-03, U-35 and U-36 first, then the rung you need.
* **Revenue layer:** R-16 before any other skill is used with real money.

## Part 0: How to use this document

### What this is

A skill tree maps capabilities and how they depend on each other. This document holds three trees of different shapes and purposes and one revenue layer they share. Agent 1 is a prerequisite ladder for mastering code. Agent 2 is a set of rings for mastering graphics from the smallest pixel outward. Agent 3 is a helix that joins logic and imagination to understand heavy fields and to learn anything new. Each skill answers: why does it exist, how is it made, what can be changed, how is it learned, how do I know it is learned, and where is the evidence.

### How the parts differ

| Part | Mastery goal | Shape | How mastery is judged |
| :--- | :--- | :--- | :--- |
| **Agent 1: Code Master** | Write, debug, read, edit, delete, learn and specialise in any code | Ladder: 5 tiers | Proof of mastery: tests, executors, proofs, sources |
| **Agent 2: Graphics Master** | Any graphics task from light to heavy, known and unknown media | Core plus 6 rings | Signs of mastery: blind readers, panels, audits, reproducible settings |
| **Agent 3: Understanding Master** | Heavy science, life, language, learning and communication | Helix: 7 rungs | Bridge test: the logic half and the imagination half agree |
| **Revenue Layer** | Turn checked work into lawful income | Pipeline: 5 stages | Proof it works: measured results, with guardrails |

### What it cannot be

No document, and no model, contains almost all knowledge in the world or an unlimited skill set. The trees specify what can be done: a broad base from pretraining (mode M1), retrieval and tools for what is not stored (M6), and a verified learning loop (M3, M7). For a deployed model, 'learned' means stored in context, files or memory unless the weights are trained. 'Imagination' and 'intuition' for a language model are working metaphors for fast, varied pattern completion, not claims about experience.

### Card fields

### Evidence grades

* **A:** established theory, standard or textbook knowledge.
* **B:** results benchmarked in humans or models (peer reviewed or reproducible).
* **C:** emerging, contested or practitioner-originated. 
*Grades describe the skill's evidence base, not the agent's competence.*

### Rules that apply to every skill

* **Verify before trusting.** Self-generated output without an outside check is not evidence; self-correction alone is unreliable (L-32).
* **Reversible by default.** Deletion follows L-04: dry run, snapshot, confirm, verify.
* **Defensive and lawful.** Security skills are for systems you are authorised to work on; no malware, no deception, no unauthorised access.
* **Education, not advice.** Finance, tax, legal, health and chemistry safety topics are taught as method; decisions stay with qualified humans.
* **Respect originality and rights.** Cite, quote sparingly, keep licence records, check outputs for copies (G-35).
* **Label the unknown.** Mark claims as established, supported, speculative or unknown, with dates (U-35).
* **Approve money.** No payment, contract, new account or public statement without human approval (R-16).

### Source verification status

Every source is given by a stable identifier (arXiv number, DOI or official address) plus title and venue, so it can be found even if a web address changes. During preparation the ICM paper identifier and repository, the Absolute Zero paper and the OMNI paper were opened and read. All other identifiers are the canonical ones from the literature but were not each opened; confirm any source before citing it in a thesis. Statements about science frontiers (dark matter, dark energy, cosmic tensions, origin of life, quantum interpretations) reflect the literature as known to the author and must be re-checked against current papers. Legal and tax notes use United States sources as examples and are not legal or tax advice.

## Part I: Code Master: the logic tree

Agent 1 is the Code Master: logic applied to every stage of software work. Its tiers run from the ground (read, write, edit, delete, shell, history, builds) through craft, quality and specialisation to mastery (learning anything new, autonomy, depth, proof, architecture). Wherever a checker exists (tests, an executor, a type checker, a proof kernel, a source file) the agent uses it and treats unchecked output as a draft. Typical settings: low sampling temperature, tests as the reward, stage-gated work, human approval for deletion and deployment.

Main failure modes: plausible but wrong code, over-trust in self-verification, silent destructive edits, insecure code, and context overload. Each skill names its own limits.

### The tree (Prerequisite ladder)

* **Tier 0 Ground (L-01 to L-07):** Exact reading of code and files; Writing code from a specification; Surgical editing; Reversible deletion and cleanup; Shell and terminal fluency; Version control mastery; Environments, dependencies and builds.
* **Tier 1 Craft (L-08 to L-14):** Algorithm design and analysis; Data structures and representations; Language fundamentals and paradigms; Python mastery; C and C++ mastery; JavaScript and TypeScript; Rust and Go.
* **Tier 2 Quality (L-15 to L-22):** Specification to tests; Debugging method; Reading logs, traces and debuggers; Refactoring and legacy code; Code review and design critique; Performance engineering; Security engineering (defensive); Static analysis and type systems.
* **Tier 3 Specialisations (L-23 to L-30):** Back-end services and APIs; Front-end engineering; Mobile and Android development; Systems, operating systems and networking; Databases and distributed systems; Data, machine learning and local LLMs; DevOps, CI/CD and observability; Compilers, interpreters and domain languages.
* **Tier 4 Mastery (L-31 to L-36):** Learning any new language or framework fast; The self-learning loop for code; Agentic coding and ICM workspaces; Specialist depth; Formal verification and proof; Large-scale design and architecture.

### Tier 0 Ground

#### L-01 Exact reading of code and files
* **Why it exists:** Every change starts with an accurate picture of what exists. Misreading is the root of most bad edits.
* **How it is made / works:** Map the repository (tree, entry points, build files), read top-down from the entry point, trace data flow and calls for the task, note invariants and unknowns, then confirm by running or searching instead of guessing. Open the smallest range that answers the question; models lose mid-document detail in long contexts.
* **What you can change:** Depth versus breadth, tools (grep, symbol index, debugger), how every claim is anchored (file and line).
* **How it is learned:** Modes M5, M6. Practise on unfamiliar open-source repositories: answer 'where is X handled and why' with file:line anchors, then verify by execution.
* **Proof of mastery:** Twenty repository questions answered with anchors that match actual behaviour; no invented functions or options.
* **Sources:** [27] Liu et al. 2024; [28] Yang et al. 2024; [29] Jimenez et al. 2024; [30] Shotts: The Linux Command Line. *(Evidence B)*

#### L-02 Writing code from a specification
* **Why it exists:** Working code begins as a precise statement of what must be true. Fluent code that was never run is a draft.
* **How it is made / works:** Restate the requirement, list inputs, outputs and edge cases, write tests or examples first, implement the smallest correct version, run it, then clean up. Execution is the judge, since models produce plausible but wrong code.
* **What you can change:** Size of each step, test-first or test-after, language idioms, how much is generated at once.
* **How it is learned:** Modes M3, M5, M6. Solve benchmark problems against hidden tests and real small tasks; use test results as the reward; keep a catalogue of failure classes.
* **Proof of mastery:** High first-attempt pass rate on held-out problems, with tests that were written before the code.
* **Sources:** [31] Chen et al. 2021; [32] Austin et al. 2021; [29] Jimenez et al. 2024; [33] Gao et al. 2023. *(Evidence B)*

#### L-03 Surgical editing
* **Why it exists:** Edits fail through collateral damage. The smallest change that passes the check protects everything that already works.
* **How it is made / works:** Read, state the hypothesis, make the smallest change (patch or diff, not a whole-file rewrite), re-run the check, review the diff line by line. The editing interface itself (viewer, editor, linter feedback) measurably changes success.
* **What you can change:** Edit granularity, diff format, test gate, maximum files per change.
* **How it is learned:** Modes M3, M5. Work through real issues; read many diffs before writing any; use tests as reward; add each failure pattern as a rule.
* **Proof of mastery:** The patch passes tests and the diff touches only intended lines.
* **Sources:** [28] Yang et al. 2024; [29] Jimenez et al. 2024; [34] Git project: git-diff documentation; [35] Chacon & Straub: Pro Git. *(Evidence B)*

#### L-04 Reversible deletion and cleanup
* **Why it exists:** Deleting is the one operation that re-running cannot undo. Removing dead code, files and dependencies is still essential.
* **How it is made / works:** Dry-run list, check nothing depends on the targets (search references, run tests), commit a snapshot or move to trash, delete, verify. Above a threshold (count, size, unfamiliar path) require human confirmation. Treat globs, symlinks and spaces in names as hazards.
* **What you can change:** Confirmation threshold, trash versus hard delete, allow-listed folders, retention window.
* **How it is learned:** Modes M5. Rehearse only in sandboxes; build adversarial path tests; study incident reports for failure shapes.
* **Proof of mastery:** Zero out-of-scope deletions across an adversarial test suite, and every deletion is recoverable.
* **Sources:** [36] freedesktop.org: Trash specification; [37] GNU Project: GNU Coreutils Manual; [38] The Open Group: POSIX.1-2017 Base Specifications; [39] Beyer et al.: Site Reliability Engineering (Google); [40] Amodei et al. 2016. *(Evidence A)*

#### L-05 Shell and terminal fluency
* **Why it exists:** The terminal is the control surface for almost everything an agent does on a machine, including Android through Termux.
* **How it is made / works:** Pipes, redirection, quoting, exit codes, globbing, process control and scripting. Safe scripts fail early, quote every variable and never run unreviewed downloaded code. Termux adds its own package manager, no root, and Android limits on background processes.
* **What you can change:** POSIX portability versus Bash features, strictness flags, logging, how much is scripted versus run by hand.
* **How it is learned:** Modes M5, M6. Write twenty small scripts, lint each, and run them on a clean environment; study the Termux wiki for platform limits.
* **Proof of mastery:** Scripts pass the linter, handle spaces and errors, and run unchanged on a fresh environment.
* **Sources:** [30] Shotts: The Linux Command Line; [41] GNU Project: GNU Bash Reference Manual; [37] GNU Project: GNU Coreutils Manual; [38] The Open Group: POSIX.1-2017 Base Specifications; [42] MIT CSAIL: The Missing Semester of Your CS Education; [43] Termux: Termux Wiki; [44] ShellCheck project: ShellCheck. *(Evidence A)*

#### L-06 Version control mastery
* **Why it exists:** History is the safety net for every other skill: it makes change reversible and explainable.
* **How it is made / works:** Small commits with clear messages, branches, rebase and merge, conflict resolution, bisect to find the commit that broke something, reflog to recover lost work.
* **What you can change:** Branching model, commit size, rebase versus merge, signing and review rules.
* **How it is learned:** Modes M5, M6. Recover from seeded disasters (lost commit, bad merge, wrong force-push) in a sandbox repository.
* **Proof of mastery:** Five seeded disasters recovered without data loss and with a clean history.
* **Sources:** [35] Chacon & Straub: Pro Git; [34] Git project: git-diff documentation; [45] Git project: git-bisect documentation; [42] MIT CSAIL: The Missing Semester of Your CS Education. *(Evidence A)*

#### L-07 Environments, dependencies and builds
* **Why it exists:** Code that only runs on one machine is not finished. Reproducible builds make results trustworthy.
* **How it is made / works:** Isolated environments, pinned dependencies and lock files, one-command builds (make, CMake, npm, cargo), containers when needed, configuration through environment variables, no secrets in code.
* **What you can change:** Pinning strictness, container versus virtualenv, build system choice.
* **How it is learned:** Modes M5, M6. Take ten real projects, build each from the README on a clean environment, and record every missing step.
* **Proof of mastery:** A fresh machine builds and tests the project from the README in one command.
* **Sources:** [46] Python Packaging Authority: Python Packaging User Guide; [47] Docker documentation; [48] Wiggins: The Twelve-Factor App; [49] Kitware: CMake documentation. *(Evidence A)*

### Tier 1 Craft: algorithms, data structures and languages

#### L-08 Algorithm design and analysis
* **Why it exists:** Choosing the right algorithm often matters more than any optimisation.
* **How it is made / works:** State the problem and invariants, pick a paradigm (greedy, divide and conquer, dynamic programming, graph search), prove or test correctness, analyse time and space. Stress-test against a brute-force solution on small inputs.
* **What you can change:** Exact versus approximate, memory versus time, worst case versus average case.
* **How it is learned:** Modes M3, M5. Solve graded problem sets; always compare with brute force; use passing tests as reward.
* **Proof of mastery:** Correct and within complexity limits on adversarial stress tests.
* **Sources:** [50] Erickson: Algorithms; [51] MIT OpenCourseWare; [52] Abelson & Sussman: SICP; [31] Chen et al. 2021. *(Evidence A)*

#### L-09 Data structures and representations
* **Why it exists:** How data is laid out decides speed, memory and bugs.
* **How it is made / works:** Arrays, hash maps, trees, heaps, graphs, tries and probabilistic structures; choose by access pattern and memory layout; keep representations that make illegal states impossible.
* **What you can change:** Cache behaviour, mutability, serialisation format, index design.
* **How it is learned:** Modes M5. Implement each structure from scratch, then benchmark against the standard library.
* **Proof of mastery:** Implementations pass property tests and match library performance within a stated factor.
* **Sources:** [50] Erickson: Algorithms; [51] MIT OpenCourseWare; [53] cppreference.com; [54] Hypothesis project: property-based testing for Python. *(Evidence A)*

#### L-10 Language fundamentals and paradigms
* **Why it exists:** Understanding what languages share makes every new language fast to learn.
* **How it is made / works:** Scope, types, memory management, evaluation order, concurrency models, error handling, modules. Compare imperative, functional, object-oriented and logic styles on the same problem.
* **What you can change:** Static or dynamic typing, garbage collection or ownership, how errors are represented.
* **How it is learned:** Modes M5, M6. Solve the same five tasks in four languages and write a comparison of what each made easy or hard.
* **Proof of mastery:** Predicts the behaviour of unfamiliar code in a new language from concepts alone.
* **Sources:** [52] Abelson & Sussman: SICP; [55] Nystrom: Crafting Interpreters; [56] Rosetta Code; [57] Klabnik & Nichols: The Rust Programming Language. *(Evidence A)*

#### L-11 Python mastery
* **Why it exists:** Python is the default language for automation, data and AI work.
* **How it is made / works:** The data model, iterators and generators, context managers, typing, standard library, packaging, async I/O, and when to call native code for speed. Follow the style guide and type-check.
* **What you can change:** Type strictness, sync versus async, packaging layout, dependency policy.
* **How it is learned:** Modes M5, M6. Build a command-line tool, a library and an async service, each with tests, types and packaging.
* **Proof of mastery:** A package with tests and strict type checks that installs cleanly and passes review.
* **Sources:** [58] Python 3 documentation; [59] PEP 8; [46] Python Packaging Authority; [60] mypy documentation; [54] Hypothesis project. *(Evidence B)*

#### L-12 C and C++ mastery
* **Why it exists:** Native code runs close to the machine and is unforgiving: memory errors become security holes.
* **How it is made / works:** Ownership and lifetimes (RAII), undefined behaviour, templates and the standard library, build systems, and debugging with a debugger and sanitizers.
* **What you can change:** Language standard, abstraction level, build flags, sanitizer coverage.
* **How it is learned:** Modes M5, M6. Write small systems with every sanitizer on; fix every report; read the core guidelines.
* **Proof of mastery:** Clean sanitizer runs, no undefined behaviour in review, and a reproducible build.
* **Sources:** [53] cppreference.com; [61] Stroustrup & Sutter: C++ Core Guidelines; [62] GDB documentation; [63] AddressSanitizer; [49] Kitware: CMake documentation. *(Evidence B)*

#### L-13 JavaScript and TypeScript
* **Why it exists:** These languages run the web and much of the tooling around it.
* **How it is made / works:** The event loop and asynchronous behaviour, modules, the DOM, Node, and static types that catch errors before running.
* **What you can change:** Strictness of types, bundler choice, runtime (browser or server).
* **How it is learned:** Modes M5, M6. Build a small browser app and a server, both fully typed and tested.
* **Proof of mastery:** No type errors, correct async behaviour under test, and a working build.
* **Sources:** [64] ECMAScript language specification; [65] Microsoft: TypeScript Handbook; [66] Mozilla: MDN Web Docs. *(Evidence B)*

#### L-14 Rust and Go
* **Why it exists:** Memory-safe systems languages and simple concurrent services are central in modern infrastructure.
* **How it is made / works:** Rust: ownership, borrowing, traits, error types. Go: goroutines, channels, interfaces, explicit errors. Learn both through small services and command-line tools.
* **What you can change:** Safety versus simplicity, concurrency model, error style.
* **How it is learned:** Modes M5, M6. Port one earlier project into each language and compare.
* **Proof of mastery:** Both ports pass the original tests and run without data races.
* **Sources:** [57] Klabnik & Nichols: The Rust Programming Language; [67] Go team: Effective Go. *(Evidence B)*

### Tier 2 Quality: testing, debugging, review, performance, security

#### L-15 Specification to tests
* **Why it exists:** Tests turn intent into a checker the agent can run repeatedly.
* **How it is made / works:** Unit, integration and end-to-end tests, test-first design, property-based testing that checks general rules on generated inputs, and mutation checks that test the tests.
* **What you can change:** Test pyramid balance, generator strength, coverage target, flakiness policy.
* **How it is learned:** Modes M3, M5. Write tests for existing code, then break the code deliberately to see if the tests catch it.
* **Proof of mastery:** The suite fails on seeded bugs and passes on correct code.
* **Sources:** [54] Hypothesis project; [68] Claessen & Hughes 2000; [69] Winters, Manshreck & Wright: Software Engineering at Google. *(Evidence A)*

#### L-16 Debugging method
* **Why it exists:** Most engineering time is spent finding why code does not do what was intended.
* **How it is made / works:** Reproduce, minimise the failing case, form a hypothesis, test it (bisect or print or debugger), fix the root cause, add a regression test. Treat it as the scientific method with an executable experiment.
* **What you can change:** Order of hypotheses, tooling, how small the minimal case must be.
* **How it is learned:** Modes M3, M5, M6. Debug seeded bugs and real issues; keep a log of cause, signal and fix.
* **Proof of mastery:** Seeded bugs are found by method rather than luck, each with a regression test.
* **Sources:** [70] Zeller et al.: The Debugging Book; [45] Git project: git-bisect documentation; [71] Stanford Encyclopedia of Philosophy: Scientific Method; [28] Yang et al. 2024. *(Evidence B)*

#### L-17 Reading logs, traces and debuggers
* **Why it exists:** Evidence from a running system is more reliable than reasoning about code alone.
* **How it is made / works:** Read stack traces from the bottom of the cause, use logs with context, set breakpoints and watchpoints, inspect memory, use browser developer tools and tracing for distributed calls.
* **What you can change:** Log level and format, sampling of traces, which tool for which layer.
* **How it is learned:** Modes M5, M6. Diagnose provided failure dumps and live problems from evidence only.
* **Proof of mastery:** Root cause identified from the evidence alone in a set of seeded failures.
* **Sources:** [62] GDB documentation; [72] Chrome DevTools documentation; [70] Zeller et al.: The Debugging Book; [39] Beyer et al.: Site Reliability Engineering (Google). *(Evidence B)*

#### L-18 Refactoring and legacy code
* **Why it exists:** Old code is where most work happens, and rewrites usually cost more than expected.
* **How it is made / works:** Add characterisation tests that pin current behaviour, make small behaviour-preserving steps from a catalogue, replace parts gradually, and keep the system working throughout.
* **What you can change:** Step size, how much to rewrite, module boundaries.
* **How it is learned:** Modes M5, M6. Take a messy open-source module, pin its behaviour, and refactor in steps with tests green.
* **Proof of mastery:** Behaviour is unchanged by tests and the structure measurably improves.
* **Sources:** [73] Fowler: Refactoring catalog; [74] Parnas 1972; [69] Winters, Manshreck & Wright: Software Engineering at Google. *(Evidence A)*

#### L-19 Code review and design critique
* **Why it exists:** A second look catches defects and spreads understanding.
* **How it is made / works:** Check correctness, clarity, tests, security, performance and fit with the design; comment on the code and give reasons; separate must-fix from preference.
* **What you can change:** Review depth, checklist, who reviews what.
* **How it is learned:** Modes M2, M5. Review real pull requests and compare with maintainers' comments.
* **Proof of mastery:** Finds the defects that human reviewers found, with fewer false alarms.
* **Sources:** [75] Google Engineering Practices: code review; [69] Winters, Manshreck & Wright: Software Engineering at Google. *(Evidence B)*

#### L-20 Performance engineering
* **Why it exists:** Speed and memory use decide cost and user experience, and guesses about bottlenecks are usually wrong.
* **How it is made / works:** Measure first, profile (flame graphs), fix algorithmic problems before micro-optimisations, mind memory layout and I/O, re-measure. Premature optimisation is a known trap.
* **What you can change:** Target metric, profiler, caching strategy, parallelism.
* **How it is learned:** Modes M5, M6. Profile slow programs, predict the bottleneck, then check the prediction.
* **Proof of mastery:** A measured improvement with no behaviour change, and the cause predicted correctly.
* **Sources:** [76] Gregg: Flame graphs; [77] Knuth 1974; [50] Erickson: Algorithms. *(Evidence A)*

#### L-21 Security engineering (defensive)
* **Why it exists:** Code that works but is exploitable causes real harm. This skill is for defending systems you are authorised to work on.
* **How it is made / works:** Threat modelling, input validation, authentication and authorisation, secret handling, memory safety, dependency risk and, for language-model agents, prompt-injection defences and least-privilege tools. Never write malware or attack systems without permission.
* **What you can change:** Threat model scope, trust boundaries, which actions require approval.
* **How it is learned:** Modes M5, M6. Review deliberately vulnerable practice applications; fix each class of flaw and add a test.
* **Proof of mastery:** Seeded vulnerabilities found and fixed with regression tests, and no unauthorised testing.
* **Sources:** [78] OWASP Top 10 Web Application Security Risks; [79] OWASP Top 10 for Large Language Model Applications; [80] Greshake et al. 2023; [40] Amodei et al. 2016. *(Evidence B)*

#### L-22 Static analysis and type systems
* **Why it exists:** Machines can check large classes of errors before the program ever runs.
* **How it is made / works:** Linters, type checkers, sanitizers and shell analysers; designing types so wrong programs do not compile; reading and triaging tool output.
* **What you can change:** Strictness, which rules are enforced in CI, suppression policy.
* **How it is learned:** Modes M5. Turn on the strictest settings for old projects and fix the findings.
* **Proof of mastery:** Strict checks pass in CI and each suppression is justified.
* **Sources:** [60] mypy documentation; [65] TypeScript Handbook; [44] ShellCheck project; [63] AddressSanitizer. *(Evidence A)*

### Tier 3 Specialisations

#### L-23 Back-end services and APIs
* **Why it exists:** Most software value is delivered through services that other programs call.
* **How it is made / works:** HTTP semantics, resource design, authentication, idempotency, rate limits, queues and background jobs, configuration and logging in the twelve-factor style.
* **What you can change:** API style, auth method, consistency of errors, versioning.
* **How it is learned:** Modes M5, M6. Build and test a small service with a documented API and failure handling.
* **Proof of mastery:** Passes contract tests including bad input, timeouts and repeated requests.
* **Sources:** [81] RFC 9110: HTTP Semantics; [48] Wiggins: The Twelve-Factor App; [66] Mozilla: MDN Web Docs; [82] PostgreSQL documentation. *(Evidence B)*

#### L-24 Front-end engineering
* **Why it exists:** The interface is where users judge everything else.
* **How it is made / works:** Component-based reactive UI, state management, rendering cost, accessibility and responsive layout, build tooling and testing.
* **What you can change:** State architecture, rendering strategy, accessibility level.
* **How it is learned:** Modes M5, M6. Build a data-driven interface and audit it for accessibility and speed.
* **Proof of mastery:** Passes accessibility checks and performance budgets, with tested components.
* **Sources:** [83] Meta: React documentation; [66] Mozilla: MDN Web Docs; [84] WCAG 2.2; [85] Google: web.dev Learn. *(Evidence B)*

#### L-25 Mobile and Android development
* **Why it exists:** Phones are the most widespread computers, with strict lifecycle, permission and battery rules.
* **How it is made / works:** App components and lifecycle, Kotlin or Java, permissions, background work limits, storage, packaging and signing; integration with Termux and its API for automation.
* **What you can change:** Native versus cross-platform, background strategy, permission scope.
* **How it is learned:** Modes M5, M6. Build a small app and a Termux-driven automation; test on a real device.
* **Proof of mastery:** Installs, survives lifecycle changes and background limits, and requests only needed permissions.
* **Sources:** [86] Android Developers documentation; [87] Kotlin documentation; [43] Termux Wiki. *(Evidence B)*

#### L-26 Systems, operating systems and networking
* **Why it exists:** Everything runs on processes, memory, files and sockets; understanding them explains many mysterious bugs.
* **How it is made / works:** Processes and threads, virtual memory, file systems, system calls, TCP/IP, sockets and event loops; build small servers and tools from the ground up.
* **What you can change:** Blocking versus non-blocking I/O, protocol design, buffer sizes.
* **How it is learned:** Modes M5, M6. Write a small shell, a file tool and a network server, then trace their system calls.
* **Proof of mastery:** Working tools whose resource use and failure behaviour are explained from first principles.
* **Sources:** [88] Arpaci-Dusseau & Arpaci-Dusseau: Operating Systems: Three Easy Pieces; [89] Beej's Guide to Network Programming; [90] Nand to Tetris. *(Evidence A)*

#### L-27 Databases and distributed systems
* **Why it exists:** Data outlives code, and distribution adds partial failure.
* **How it is made / works:** Relational modelling, indexes, transactions and isolation, query plans; replication, consensus, ordering of events, and the trade-offs of consistency and availability.
* **What you can change:** Isolation level, schema design, replication mode.
* **How it is learned:** Modes M5, M6. Design a schema, load realistic data, tune queries, and simulate node failures.
* **Proof of mastery:** Queries use intended indexes, transactions are correct under concurrency, and failure behaviour is predicted.
* **Sources:** [82] PostgreSQL documentation; [91] SQLite documentation; [92] Ongaro & Ousterhout 2014; [93] Lamport 1978. *(Evidence A)*

#### L-28 Data, machine learning and local LLMs
* **Why it exists:** Local models, fine-tuning and data pipelines let an agent run and adapt without depending on outside services.
* **How it is made / works:** Data cleaning and splits, training loops and evaluation, parameter-efficient fine-tuning, quantisation, and local inference. Evaluate on held-out data and never on training data.
* **What you can change:** Model size, quantisation level, fine-tuning method, evaluation set.
* **How it is learned:** Modes M2, M5, M6. Train a tiny model from scratch, fine-tune a small one, and run quantised inference on a phone-class machine.
* **Proof of mastery:** Held-out evaluation shows a measured gain, and the model runs within the stated memory limit.
* **Sources:** [94] Goodfellow et al.: Deep Learning; [95] Karpathy: Neural Networks: Zero to Hero; [6] Hu et al. 2021; [96] Dettmers et al. 2023; [97] llama.cpp; [98] Hugging Face Transformers documentation; [1] Vaswani et al. 2017. *(Evidence B)*

#### L-29 DevOps, CI/CD and observability
* **Why it exists:** Reliable delivery needs automation and visibility.
* **How it is made / works:** Continuous integration and deployment, containers, infrastructure as code, metrics, logs and traces, alerting, incident response and postmortems.
* **What you can change:** Pipeline stages, alert thresholds, rollback method.
* **How it is learned:** Modes M5, M6. Build a pipeline that tests, builds and deploys a small service, then break it and diagnose from telemetry.
* **Proof of mastery:** A change reaches production only through green checks, and a seeded fault is found from telemetry.
* **Sources:** [39] Beyer et al.: Site Reliability Engineering (Google); [47] Docker documentation; [99] GitHub Actions documentation; [48] Wiggins: The Twelve-Factor App. *(Evidence B)*

#### L-30 Compilers, interpreters and domain languages
* **Why it exists:** Building a language shows how all code is understood by machines and lets you create the right notation for a problem.
* **How it is made / works:** Lexing, parsing into trees, semantic checks, intermediate forms, interpreters and virtual machines; design a small language with a grammar and tests first.
* **What you can change:** Syntax weight, typing, interpreter versus compiler.
* **How it is learned:** Modes M5, M6. Build an interpreter and a small domain language from a textbook.
* **Proof of mastery:** The interpreter passes its conformance suite and a newcomer completes tasks in the small language.
* **Sources:** [55] Nystrom: Crafting Interpreters; [52] Abelson & Sussman: SICP; [90] Nand to Tetris. *(Evidence A)*

### Tier 4 Mastery: learning, autonomy, depth, proof, architecture

#### L-31 Learning any new language or framework fast
* **Why it exists:** The required technology changes constantly. The skill is to become productive in anything quickly and correctly.
* **How it is made / works:** Map its concepts to ones already known, read the official tutorial and reference, set up the toolchain (build, test, package), learn idioms from the standard library and style guide, port a known small project, then read real code and get feedback from linters and tests.
* **What you can change:** Which known language is the anchor, size of the first project, depth of reading before coding.
* **How it is learned:** Modes M5, M6. Learn one new language per month this way; keep a note of the concept map and the traps found.
* **Proof of mastery:** A working, tested, idiomatic project in a new language within days, passing a style check.
* **Sources:** [100] Ericsson et al. 1993; [101] Chi et al. 1989; [102] Pan & Yang 2010; [56] Rosetta Code. *(Evidence B)*

#### L-32 The self-learning loop for code
* **Why it exists:** Fixed weights mean improvement must be engineered. Tests give code a real checker to learn from.
* **How it is made / works:** Choose tasks, attempt, run the tests, reflect on failures in words, store a lesson in a skill file, retry on new tasks. Unit tests are a reliable reward; self-correction without an outside check is not.
* **What you can change:** Task source, verifier, lesson storage, whether lessons train weights.
* **How it is learned:** Modes M3, M7. Run the loop on benchmark issues; retest old skills after each lesson.
* **Proof of mastery:** Measured gain on held-out issues, and no gain is claimed where no verifier exists.
* **Sources:** [20] Zelikman et al. 2022; [22] Shinn et al. 2023; [21] Madaan et al. 2023; [23] Huang et al. 2024; [8] Zhao et al. 2025; [29] Jimenez et al. 2024. *(Evidence B)*

#### L-33 Agentic coding and ICM workspaces
* **Why it exists:** Real tasks need plans, tools and memory over many steps, with a human in control.
* **How it is made / works:** Plan, call tools, observe, repair, stop at a budget. Jake Van Clief's ICM organises the agent's context as folders and plain-text stage contracts so the right files load at the right moment and humans can edit any step.
* **What you can change:** Number of stages, checkpoints, tool permissions, memory policy.
* **How it is learned:** Modes M5, M6. Build a coding workspace with stages for plan, implement, test and review; run it on real tasks.
* **Proof of mastery:** Tasks complete within the step budget, each stage output is editable, and no unapproved side effects occur.
* **Sources:** [18] Yao et al. 2023; [28] Yang et al. 2024; [19] Packer et al. 2023; [15] Van Clief 2026; [103] Interpretable-Context-Methodology reference implementation; [104] ICM core conventions; [105] Anthropic 2024. *(Evidence B)*

#### L-34 Specialist depth
* **Why it exists:** Breadth gets work started; depth in a niche earns trust and income.
* **How it is made / works:** Choose a niche, read the source of leading projects, reproduce key papers or benchmarks, contribute fixes upstream, and practise deliberately on the hardest sub-problems. Expertise needs a domain with stable regularities and feedback.
* **What you can change:** Niche choice, depth versus breadth, contribution target.
* **How it is learned:** Modes M5, M6. Pick a niche for 90 days; set reproducible milestones and review them.
* **Proof of mastery:** A reproduced result and an accepted upstream contribution in the niche.
* **Sources:** [100] Ericsson et al. 1993; [106] Kahneman & Klein 2009; [69] Winters, Manshreck & Wright: Software Engineering at Google. *(Evidence B)*

#### L-35 Formal verification and proof
* **Why it exists:** For critical code, tests show presence of bugs and proofs show absence under stated assumptions.
* **How it is made / works:** State the specification formally, model the system, check with a model checker or prove in a proof assistant, and keep the proof in the repository with the code.
* **What you can change:** Which properties are proved, level of automation, assumptions.
* **How it is learned:** Modes M3, M5. Work through interactive textbooks; prove properties of small algorithms and protocols.
* **Proof of mastery:** Machine-checked proofs of stated properties for a small verified component.
* **Sources:** [107] Theorem Proving in Lean 4; [108] Mathematics in Lean; [109] Software Foundations; [110] TLA+ Home Page; [111] Jiang et al. 2023; [112] Yang et al. 2023. *(Evidence A)*

#### L-36 Large-scale design and architecture
* **Why it exists:** Systems fail from poor boundaries more often than from poor code.
* **How it is made / works:** Split by what is likely to change, define stable interfaces, record decisions and trade-offs, plan for failure and evolution, and keep the design small enough to understand.
* **What you can change:** Module boundaries, coupling, which decisions are reversible.
* **How it is learned:** Modes M5, M6. Write design documents for three systems and have them reviewed against failure scenarios.
* **Proof of mastery:** The design survives a review of failure and change scenarios without rework of its core.
* **Sources:** [74] Parnas 1972; [69] Winters, Manshreck & Wright: Software Engineering at Google; [39] Beyer et al.: Site Reliability Engineering (Google); [48] Wiggins: The Twelve-Factor App. *(Evidence A)*

## Part II: Graphics Master: the imagination tree

Agent 2 is the Graphics Master: imagination organised from the smallest pixel to the widest world. An imagination core (ideas, taste, art direction) feeds six rings: pixel and light, mark and type, image and composition, system and interface, motion and world, and machine imagination with the unknown. Any graphics task, light or heavy, maps to a ring; media that do not exist yet are handled by the entry protocol in G-36. Typical settings: higher sampling variety, constraints and references, panel judgement, reproducible seeds and logs.

Main failure modes: cliche, hidden copying, unlabelled composites, inaccessible design, uncontrolled generation, and wrong output formats. Mastery is judged by readers, panels and technical checks, so each card lists signs of mastery with its failure mode.

### The tree

* **Core (G-01 to G-03):** The ideation engine; Taste, critique and iteration; Art direction: from brief to visual strategy.
* **Ring 1 Pixel and light (G-04 to G-09):** Pixels, resolution and bit depth; Colour theory, perception and management; Light, shadow and form; Raster editing and retouching; Vector construction; Formats, compression and export pipelines.
* **Ring 2 Mark and type (G-10 to G-14):** Drawing and mark-making; Typography; Icon and symbol design; Logo and lettering design; Pattern, texture and ornament.
* **Ring 3 Image and composition (G-15 to G-20):** Composition and visual hierarchy; Illustration; Photo editing, compositing and photographic direction; Diagrams, infographics and data visualisation; Concept art and storyboarding; Print and editorial layout.
* **Ring 4 System and interface (G-21 to G-25):** Interface visual design; Design systems and tokens; Brand identity systems; Presentation and information design; Marketing, social and advertising graphics.
* **Ring 5 Motion and world (G-26 to G-32):** Motion graphics and animation; Video editing and compositing; 3D modelling, sculpting and texturing; Rendering, lighting and shaders; Game and real-time art; Generative and creative-coding art; AR, VR and interactive spatial experiences.
* **Ring 6 Machine and unknown (G-33 to G-36):** AI image and video generation craft; Programmatic and automated graphics pipelines; Style, reference, originality and rights; Entering an unknown visual category.

### Imagination core: ideas, taste, direction

#### G-01 The ideation engine
* **Why it matters:** Every visual task begins with finding an idea worth making, and the first idea is rarely the best one.
* **How it works:** Gather references and a moodboard, diverge widely (many sketches, metaphors, constraints, unlikely combinations), cluster, then pick a few directions to develop. Sampling variety and forced association widen the set; a structured brief keeps it relevant.
* **Ways to vary it:** Number of ideas, constraint type, reference distance, which directions are carried forward.
* **How it is learned:** Modes M5, M7. Run daily thumbnail and concept rounds from set briefs; score fluency, flexibility and originality; compare with single-pass attempts.
* **Signs of mastery:** Idea sets beat a single pass on blind originality while fitting the brief. Failure mode: variety with no fit to purpose.
* **Sources:** [113] Guilford 1950; [114] Mednick 1962; [115] Gentner 1983; [116] Holtzman et al. 2020; [117] Si et al. 2025; [118] Chakrabarty et al. 2024. *(Evidence B)*

#### G-02 Taste, critique and iteration
* **Why it matters:** Without a checker, taste decides quality. Critique converts vague dislike into specific improvement.
* **How it works:** Compare work with strong references, name what works and what does not (hierarchy, balance, contrast, rhythm, clarity), change one thing at a time, and compare versions blind. Model judges often agree with people but show biases such as favouring longer or first-shown options.
* **Ways to vary it:** Reference set, criteria, number of judges, blind or open comparison.
* **How it is learned:** Modes M4, M5. Pairwise comparisons with written reasons; test predictions against human panels.
* **Signs of mastery:** Predictions match a panel at a stated level and each revision names its change. Failure mode: one narrow taste making everything look alike.
* **Sources:** [119] Zheng et al. 2023; [120] Stanford Encyclopedia of Philosophy: Aesthetics; [121] Vitsoe: Dieter Rams; [122] Design Council: The Double Diamond. *(Evidence B)*

#### G-03 Art direction: from brief to visual strategy
* **Why it matters:** Beautiful work that misses the brief fails. A visual strategy aligns audience, message, style and constraints.
* **How it works:** Clarify the audience, goal, message, tone, deliverables, formats and constraints; define the visual idea in one sentence; choose palette, type, imagery and layout rules; check each piece against that sentence. The double-diamond pattern alternates widening and narrowing.
* **Ways to vary it:** How tight the brief is, number of directions shown, who approves what.
* **How it is learned:** Modes M5, M6. Write strategies for ten briefs, then test whether others can reproduce the intended look from the strategy alone.
* **Signs of mastery:** Reviewers can predict the style from the strategy, and delivered pieces match the brief. Failure mode: strategy words with no visual consequence.
* **Sources:** [122] Design Council: The Double Diamond; [121] Vitsoe: Dieter Rams; [123] Material Design 3; [124] Nielsen: 10 Usability Heuristics. *(Evidence A)*

### Ring 1 Pixel and light

#### G-04 Pixels, resolution and bit depth
* **Why it matters:** Everything on screen is a grid of samples. Understanding the grid prevents blur, banding and wrong sizes.
* **How it works:** Pixels per inch versus pixel dimensions, scaling and resampling, anti-aliasing, alpha transparency, bit depth and banding, and dithering. Choose the working size for the final use before starting.
* **Ways to vary it:** Working resolution, resampling method, bit depth, transparency handling.
* **How it is learned:** Modes M5, M6. Export the same artwork for phone, print and web and inspect the differences at pixel level.
* **Signs of mastery:** Outputs stay sharp at the target size with no banding or fringes. Failure mode: scaling raster images up and calling it high resolution.
* **Sources:** [125] W3C PNG Specification; [126] Google web.dev Learn: Images; [127] ImageMagick documentation; [128] Pillow documentation. *(Evidence A)*

#### G-05 Colour theory, perception and management
* **Why it matters:** Colour sets mood, hierarchy and accessibility, and it changes between screens and print.
* **How it works:** Hue, value and saturation; perceptual colour spaces for even gradients; contrast for legibility; colour-blind safety; colour profiles and conversion between screen and print.
* **Ways to vary it:** Colour space, palette size, contrast target, profile.
* **How it is learned:** Modes M5, M6. Rebuild ten palettes in a perceptual space, check contrast, and soft-proof for print.
* **Signs of mastery:** Palettes read clearly, pass contrast checks, and survive conversion. Failure mode: colours that look fine on one screen only.
* **Sources:** [129] CSS Color Module Level 4; [130] Ottosson 2020 (Oklab); [131] International Color Consortium; [84] WCAG 2.2; [132] ColorBrewer. *(Evidence A)*

#### G-06 Light, shadow and form
* **Why it matters:** Light gives volume, mood and focus. It is the same craft in painting, photography, 3D and interface depth.
* **How it works:** Light direction, quality and colour; core shadow, cast shadow and bounce; value structure in a few steps; materials as responses to light. Plan values in greyscale first.
* **Ways to vary it:** Number of lights, hardness, contrast ratio, material response.
* **How it is learned:** Modes M5. Study simple objects under single lights; repeat in drawing, photography and 3D.
* **Signs of mastery:** Forms read as solid under any lighting setup tested. Failure mode: flat or contradictory lighting.
* **Sources:** [133] Pharr et al.: Physically Based Rendering; [134] Cambridge in Colour; [135] Drawabox; [136] Blender Manual. *(Evidence A)*

#### G-07 Raster editing and retouching
* **Why it matters:** Most image work is editing existing pixels without destroying them.
* **How it works:** Layers, masks, adjustment layers, selections, healing, frequency separation, colour grading and non-destructive workflows; keep originals untouched.
* **Ways to vary it:** Tool (open-source or proprietary), destructiveness, how much to retouch.
* **How it is learned:** Modes M5, M6. Retouch a set of test images with a fully non-destructive file and compare with originals.
* **Signs of mastery:** Edits can be reversed or changed at any point and the result looks natural. Failure mode: over-retouching.
* **Sources:** [137] GIMP documentation; [138] Krita manual; [134] Cambridge in Colour; [127] ImageMagick documentation. *(Evidence A)*

#### G-08 Vector construction
* **Why it matters:** Vector shapes scale without loss, so logos, icons and illustrations depend on them.
* **How it works:** Points, curves and paths; Bezier handles with few anchor points; boolean operations; strokes and expansion; clean, minimal path structure; SVG output.
* **Ways to vary it:** Anchor density, stroke versus outline, grid, optimisation level.
* **How it is learned:** Modes M5, M6. Redraw bitmap logos as clean vectors using the fewest points.
* **Signs of mastery:** Clean paths that scale and edit easily, with valid SVG. Failure mode: traced paths with hundreds of needless points.
* **Sources:** [139] Pomax: A Primer on Bezier Curves; [140] W3C SVG 2; [66] Mozilla MDN Web Docs. *(Evidence A)*

#### G-09 Formats, compression and export pipelines
* **Why it matters:** The right file format decides quality, size, transparency and compatibility.
* **How it works:** Raster versus vector, lossy versus lossless, PNG, JPEG, WebP, SVG and PDF, colour profile embedding, sprite sheets and responsive image sets; pick by purpose and test the result.
* **Ways to vary it:** Format, quality setting, metadata stripping, size budget.
* **How it is learned:** Modes M5, M6. Export a set of assets for web, app and print, measure size and quality, and document the choices.
* **Signs of mastery:** Each export meets size and quality targets for its use. Failure mode: one format for everything.
* **Sources:** [125] W3C PNG Specification; [141] Google WebP documentation; [126] Google web.dev Learn: Images; [142] FFmpeg documentation. *(Evidence A)*

### Ring 2 Mark and type

#### G-10 Drawing and mark-making
* **Why it matters:** Drawing is thinking on paper. It trains observation of shape, proportion and perspective.
* **How it works:** Construct forms from simple solids, use perspective and proportion, make confident lines, and draw from reference and imagination. Practice is repetitive and graded.
* **Ways to vary it:** Medium, speed, reference versus invention.
* **How it is learned:** Modes M5. Follow a structured free course and keep dated drawings; compare early and late work.
* **Signs of mastery:** Drawings keep consistent perspective and proportion. Failure mode: stiff outlines with no construction underneath.
* **Sources:** [135] Drawabox; [143] Stanford Encyclopedia of Philosophy: Imagination; [144] Chase & Simon 1973. *(Evidence B)*

#### G-11 Typography
* **Why it matters:** Most graphics contain text, and type controls tone, hierarchy and legibility.
* **How it works:** Letterforms, scale ratios, line length, spacing and leading, pairing, hierarchy, OpenType features and variable fonts, plus licensing and fallbacks for web.
* **Ways to vary it:** Typeface pairing, scale, measure, contrast of weights.
* **How it is learned:** Modes M5, M6. Set the same text in ten styles and test legibility and tone with readers.
* **Signs of mastery:** Text is comfortable to read at its target size and the hierarchy is obvious. Failure mode: too many typefaces.
* **Sources:** [145] Butterick: Practical Typography; [146] Google Fonts Knowledge; [147] OpenType specification; [123] Material Design 3. *(Evidence A)*

#### G-12 Icon and symbol design
* **Why it matters:** Small symbols carry meaning instantly across languages.
* **How it works:** Grid and keylines, consistent stroke and corner rules, simple metaphors, optical alignment, and checks at small sizes and in dark and light modes.
* **Ways to vary it:** Grid size, stroke weight, fill style, metaphor choice.
* **How it is learned:** Modes M5, M6. Design a set of forty icons, then test recognition with readers.
* **Signs of mastery:** Icons are recognised at 16 pixels and look like one family. Failure mode: clever but ambiguous metaphors.
* **Sources:** [123] Material Design 3; [148] Apple Human Interface Guidelines; [140] W3C SVG 2; [124] Nielsen Usability Heuristics. *(Evidence A)*

#### G-13 Logo and lettering design
* **Why it matters:** A mark is the compact face of an identity and must work at every size and place.
* **How it works:** Research and concept, sketch many routes, reduce to the simplest form, test in one colour, small, large and reversed, then build as vector with spacing rules.
* **Ways to vary it:** Wordmark versus symbol, level of detail, colour use.
* **How it is learned:** Modes M5, M6. Create concepts for several fictional brands, test them at ten sizes and backgrounds.
* **Signs of mastery:** The mark works in one colour at small size and is distinct from existing marks. Failure mode: accidental similarity to existing marks.
* **Sources:** [121] Vitsoe: Dieter Rams; [145] Butterick: Practical Typography; [139] Pomax: A Primer on Bezier Curves; [149] US Copyright Office: Copyright and AI. *(Evidence B)*

#### G-14 Pattern, texture and ornament
* **Why it matters:** Repeated structure creates rhythm, surface and identity.
* **How it works:** Tiling and seamless repeats, symmetry groups, noise and procedural texture, hand-made texture capture, and controlling density so patterns support rather than fight the content.
* **Ways to vary it:** Repeat type, symmetry, scale, randomness.
* **How it is learned:** Modes M5, M6. Build seamless patterns by hand and by code and test them tiled.
* **Signs of mastery:** Patterns tile without visible seams and remain calm beneath text. Failure mode: patterns that overwhelm content.
* **Sources:** [150] Shiffman: The Nature of Code; [151] The Book of Shaders; [152] Quilez articles on shaders and procedural graphics; [153] p5.js. *(Evidence A)*

### Ring 3 Image and composition

#### G-15 Composition and visual hierarchy
* **Why it matters:** Composition tells the eye where to look and in what order.
* **How it works:** Grouping by proximity and similarity, figure and ground, alignment and grids, scale and contrast, whitespace, and the reading path. Test with a blurred or small version to see the hierarchy.
* **Ways to vary it:** Grid, focal point, density, symmetry.
* **How it is learned:** Modes M5. Redo ten layouts from a squint test; compare which keeps the hierarchy.
* **Signs of mastery:** The intended reading order is the one viewers follow in tests. Failure mode: everything competing for attention.
* **Sources:** [154] Wagemans et al. 2012; [155] Yablonski: Laws of UX; [121] Vitsoe: Dieter Rams; [123] Material Design 3. *(Evidence A)*

#### G-16 Illustration
* **Why it matters:** Illustration explains and evokes what photographs cannot.
* **How it works:** From idea to thumbnail to value study to colour to finish; consistent style rules (shape language, line, palette); character and environment design; clear silhouettes.
* **Ways to vary it:** Style, level of finish, shape language, medium.
* **How it is learned:** Modes M5. Complete small illustrations from briefs, each with documented stages.
* **Signs of mastery:** Silhouettes read clearly and the style stays consistent across a set. Failure mode: copying an existing artist's style too closely.
* **Sources:** [135] Drawabox; [138] Krita manual; [149] US Copyright Office: Copyright and AI. *(Evidence B)*

#### G-17 Photo editing, compositing and photographic direction
* **Why it matters:** Images are assembled and directed as often as captured.
* **How it works:** Match light direction, colour and grain when combining elements; mask cleanly; direct photography (framing, lens choice, light) so editing starts from a strong image; disclose composites where honesty requires.
* **Ways to vary it:** Realism level, disclosure, capture versus generation.
* **How it is learned:** Modes M5, M6. Composite objects into scenes, then ask others to spot the edits.
* **Signs of mastery:** Composites are consistent in light and perspective and are labelled when it matters. Failure mode: deceptive manipulation.
* **Sources:** [134] Cambridge in Colour; [137] GIMP documentation; [133] Pharr et al.: Physically Based Rendering; [149] US Copyright Office: Copyright and AI. *(Evidence B)*

#### G-18 Diagrams, infographics and data visualisation
* **Why it matters:** Visual explanations compress complexity if they encode data accurately.
* **How it works:** Choose the question, pick encodings that people read accurately (position over area over colour), use colour scales safe for colour-blind readers, annotate the message, and avoid distortion.
* **Ways to vary it:** Chart type, scale, annotation, interaction.
* **How it is learned:** Modes M5, M6. Redraw poor graphics and test comprehension with readers.
* **Signs of mastery:** Readers answer questions faster and more accurately. Failure mode: decoration that hides the data.
* **Sources:** [156] Wilke: Fundamentals of Data Visualization; [157] Cleveland & McGill 1984; [158] The Data Visualisation Catalogue; [132] ColorBrewer. *(Evidence B)*

#### G-19 Concept art and storyboarding
* **Why it matters:** Planning visually saves cost in animation, games and film.
* **How it works:** Rapid thumbnails, silhouette tests, key frames, shot types, continuity, camera and staging, and an animatic to test pacing.
* **Ways to vary it:** Number of thumbnails, fidelity, frame rate of the animatic.
* **How it is learned:** Modes M5. Storyboard a one-minute story and test it with viewers.

### Rung A Foundations of understanding

#### U-01 The mathematical language of science
* **Why it exists:** Science states its laws in mathematics, and mathematics often predicts what experiments later find.
* **How it is made (both halves):** Logic half: calculus, linear algebra, differential equations, probability and statistics, with derivations checked step by step. Intuition half: what each object means as a picture (a gradient as slope, an eigenvector as a stable direction, a distribution as a cloud of outcomes).
* **What you can change:** Level of rigour, geometric versus algebraic route, which tools are drilled.
* **How it is learned:** Modes M3, M5, M6. Work graded problem sets with computer algebra checking, and explain each result in a sentence and a sketch.
* **Bridge test:** Problems solved correctly and each answer explained in a picture that predicts a variant.
* **Sources:** [189] Deisenroth et al.: Mathematics for Machine Learning; [190] Axler: Linear Algebra Done Right; [191] Paul's Online Math Notes; [51] MIT OpenCourseWare; [192] 3Blue1Brown; [193] Wigner 1960. *(Evidence A)*

#### U-02 Modelling, abstraction and scale
* **Why it exists:** No model contains everything. Understanding means choosing what to keep at the scale that matters.
* **How it is made (both halves):** Logic half: variables, assumptions, dimensional analysis and scaling laws. Intuition half: sensing which effects dominate at a given scale. At each new scale, new laws can emerge that are not obvious from the parts.
* **What you can change:** Which variables, which scale, how many assumptions are stated.
* **How it is learned:** Modes M5, M6. Model the same system at two scales and list what changes and why.
* **Bridge test:** Each model states its assumptions and its failure scale, and predictions match data where they should.
* **Sources:** [194] Stanford Encyclopedia of Philosophy: Models in Science; [195] Anderson 1972; [196] Mahajan: Street-Fighting Mathematics; [197] Feynman Lectures on Physics. *(Evidence A)*

#### U-03 The scientific method and the evidence ladder
* **Why it exists:** It separates what is known from what is hoped, which matters most for frontier topics.
* **How it is made (both halves):** Logic half: hypothesis, prediction, test, update with Bayes, replication. Intuition half: noticing the anomaly and proposing bold explanations. Every claim is placed on a ladder: speculation, hypothesis, supported, replicated, established.
* **What you can change:** Evidence threshold per rung, how many replications are needed, prior strength.
* **How it is learned:** Modes M5, M6. Classify fifty published claims by rung and check each against replications.
* **Bridge test:** Claims are placed on the correct rung with sources, and updates follow new evidence.
* **Sources:** [71] Stanford Encyclopedia of Philosophy: Scientific Method; [198] SEP: Karl Popper; [187] SEP: Bayes' Theorem; [199] Open Science Collaboration 2015; [200] Ioannidis 2005. *(Evidence A)*

#### U-04 Computation for science
* **Why it exists:** Simulation and data analysis are the third pillar of science next to theory and experiment.
* **How it is made (both halves):** Logic half: numerical methods, error control, statistical fitting and reproducible code. Intuition half: plotting and exploring to feel what the numbers are doing before trusting a fit.
* **What you can change:** Method, step size, tolerance, how results are validated against known cases.
* **How it is learned:** Modes M3, M5, M6. Simulate systems with known answers first, then unknown ones; share code and seeds.
* **Bridge test:** Simulations reproduce known results to stated accuracy and every figure is regenerated from code.
* **Sources:** [201] SciPy documentation; [202] James et al.: An Introduction to Statistical Learning; [203] Downey: Think Bayes 2; [204] Feynman 1982. *(Evidence B)*

#### U-05 Reading the scientific literature
* **Why it exists:** Frontier knowledge lives in papers and preprints, and not all of them are right.
* **How it is made (both halves):** Logic half: find papers, read methods, check data and statistics, follow citations and replications. Intuition half: judge what is surprising and what the authors might be missing. Preprints are not yet peer reviewed.
* **What you can change:** Which databases, strictness about evidence, how many sources before accepting a claim.
* **How it is learned:** Modes M6. Read and critique ten papers per field, with a one-page summary and a list of weaknesses.
* **Bridge test:** Summaries are accurate to the paper, and critiques name real limitations confirmed by experts.
* **Sources:** [205] arXiv; [206] NASA Astrophysics Data System; [207] NCBI resources; [200] Ioannidis 2005; [199] Open Science Collaboration 2015. *(Evidence B)*

#### U-06 Picture-to-equation translation
* **Why it exists:** A result that cannot be pictured cannot be extended, and a picture that cannot be written as an equation cannot be tested.
* **How it is made (both halves):** Logic half: formal derivation. Intuition half: a diagram, a special case and a one-line reason. After each derivation, produce all three and predict a variant. Explaining examples to oneself improves understanding.
* **What you can change:** Choice of picture, special cases, size of the variant.
* **How it is learned:** Modes M5. For each topic write 'why this is true in one picture' and test a variant.
* **Bridge test:** The variant prediction is correct and the explanation survives expert review.
* **Sources:** [197] Feynman Lectures on Physics; [208] Susskind et al.: The Theoretical Minimum; [192] 3Blue1Brown; [209] Larkin & Simon 1987; [101] Chi et al. 1989. *(Evidence B)*

### Rung B Physics, including quantum

#### U-07 Mechanics, thermodynamics and statistical physics
* **Why it exists:** These theories explain motion, heat and why macroscopic behaviour emerges from countless microscopic parts.
* **How it is made (both halves):** Logic half: Lagrangian and Hamiltonian mechanics, conservation laws, entropy, the Boltzmann distribution. Intuition half: energy landscapes, flows and the picture of probability spreading into more possibilities.
* **What you can change:** Formalism, which approximations, equilibrium or not.
* **How it is learned:** Modes M5, M6. Solve problems, then simulate a gas or a pendulum and compare with the equations.
* **Bridge test:** Analytical and simulated answers agree and the entropy argument is explained in words.
* **Sources:** [197] Feynman Lectures on Physics; [208] The Theoretical Minimum; [210] Physics LibreTexts; [211] Jaynes 1957. *(Evidence A)*

#### U-08 Electromagnetism, waves and optics
* **Why it exists:** Fields and waves underlie light, radio, electronics and much of quantum theory.
* **How it is made (both halves):** Logic half: Maxwell's equations, wave solutions, boundary conditions, interference. Intuition half: field lines, ripples and how a wave bends, reflects and interferes.
* **What you can change:** Vector or differential form, ray versus wave model.
* **How it is learned:** Modes M5, M6. Derive wave equations, then simulate interference patterns.
* **Bridge test:** Simulated patterns match derived ones and limiting cases are explained.
* **Sources:** [197] Feynman Lectures on Physics; [210] Physics LibreTexts; [208] The Theoretical Minimum; [51] MIT OpenCourseWare. *(Evidence A)*

#### U-09 Special and general relativity
* **Why it exists:** Relativity redefines space and time, and its corrections are needed in practical systems such as satellite navigation.
* **How it is made (both halves):** Logic half: Lorentz transformations, spacetime intervals, the metric, geodesics and curvature. Intuition half: spacetime diagrams, light cones and the picture of mass bending the paths of free objects. Gravitational waves are a direct test.
* **What you can change:** Level of tensor formalism, weak-field approximations.
* **How it is learned:** Modes M5, M6. Work through lecture notes and compute time dilation and orbital effects numerically.
* **Bridge test:** Correctly computes relativistic effects and explains each with a spacetime diagram.
* **Sources:** [212] Carroll General Relativity Notes; [197] Feynman Lectures on Physics; [208] The Theoretical Minimum; [213] Abbott et al. 2016. *(Evidence A)*

#### U-10 Quantum mechanics
* **Why it exists:** It is the most accurately tested theory in physics and the most misunderstood.
* **How it is made (both halves):** Logic half: state vectors, observables, the Born rule, unitary evolution, entanglement, Bell inequalities, decoherence. Intuition half: amplitudes as arrows that add and cancel, with every metaphor labelled. Interpretations (Copenhagen, many-worlds, Bohmian) agree on standard predictions, and the measurement problem is not settled by consensus.
* **What you can change:** Formalism, which interpretation is used as a thinking aid, how metaphors are labelled.
* **How it is learned:** Modes M5, M6. Derive two-level systems and Bell-state statistics by hand and by simulation; write a neutral summary of each interpretation.
* **Bridge test:** Calculations match simulation and the agent states what is established versus interpretation-dependent.
* **Sources:** [214] Matuschak & Nielsen: Quantum Country; [208] The Theoretical Minimum; [215] Preskill Lecture Notes (Caltech Ph229); [216] SEP: Quantum Mechanics; [217] SEP: Copenhagen Interpretation; [218] SEP: Many-Worlds; [219] SEP: Bohmian Mechanics; [220] SEP: Bell's Theorem; [221] Schlosshauer 2004. *(Evidence A)*

#### U-11 Quantum information and computing
* **Why it exists:** Quantum computers promise advantages for specific problems and are limited by noise today.
* **How it is made (both halves):** Logic half: qubits, gates, circuits, algorithms (factoring, search), error correction and resource counts. Intuition half: interference as the engine of speed-ups. Claims of advantage are tested against improved classical methods.
* **What you can change:** Number of qubits, noise model, gate set, algorithm family.
* **How it is learned:** Modes M5, M6. Hand-derive small circuits, simulate them, and write what current hardware can and cannot do.
* **Bridge test:** Hand derivations match simulation and limits of present devices are stated correctly.
* **Sources:** [222] Preskill 2018; [215] Preskill Lecture Notes; [223] Shor 1997; [224] Grover 1996; [204] Feynman 1982; [225] Arute et al. 2019; [226] SEP: Quantum Computing. *(Evidence B)*

#### U-12 Quantum field theory and the Standard Model
* **Why it exists:** The Standard Model describes known particles and three of the four forces, and it also shows where physics is incomplete.
* **How it is made (both halves):** Logic half: fields, symmetries and gauge principles, particle content, interactions and measured parameters. Intuition half: particles as excitations of fields and forces as exchanges. Known gaps include gravity, dark matter and the origin of matter-antimatter imbalance.
* **What you can change:** Conceptual or technical level, which experiments are used as anchors.
* **How it is learned:** Modes M5, M6. Read lecture notes, use the particle data tables, and reproduce a simple cross-section estimate.
* **Bridge test:** Names the model's successes and its open questions with references.
* **Sources:** [227] Tong: QFT Lecture Notes; [228] Particle Data Group; [229] INSPIRE-HEP; [208] The Theoretical Minimum. *(Evidence A)*

### Rung C Cosmos, including dark matter

#### U-13 Cosmology
* **Why it exists:** It asks how the universe began, grew and what it is made of.
* **How it is made (both halves):** Logic half: the expansion equations, background radiation, nucleosynthesis, structure growth and fitted parameters. Intuition half: the expanding-balloon and ripple pictures, with their limits stated.
* **What you can change:** Model parameters, datasets used, assumptions.
* **How it is learned:** Modes M5, M6. Fit simple models to public data and compare with published parameter values.
* **Bridge test:** Recovers published parameters within stated errors and explains what each dataset constrains.
* **Sources:** [230] Planck Collaboration 2020; [231] Riess et al. 1998; [232] Perlmutter et al. 1999; [206] NASA ADS. *(Evidence A)*

#### U-14 Dark matter
* **Why it exists:** Most of the matter that gravity indicates is not accounted for by visible matter, and its nature remains an open question.
* **How it is made (both halves):** Logic half: evidence from galaxy rotation, gravitational lensing including colliding clusters, background radiation and structure growth; candidate particles (WIMPs, axions, sterile neutrinos) and primordial black holes; searches by direct detection, indirect detection and colliders; modified-gravity alternatives and where they struggle. Intuition half: gravity without visible mass as a hidden scaffold. As far as I know, no confirmed non-gravitational detection exists; always check current results.
* **What you can change:** Which evidence is weighted, candidate classes considered, treatment of alternatives.
* **How it is learned:** Modes M5, M6. Build an evidence table for each candidate and alternative with sources; refresh it from current literature.
* **Bridge test:** States evidence, candidates, null results and open questions accurately with sources, and does not claim a solution.
* **Sources:** [233] Rubin & Ford 1970; [234] Clowe et al. 2006; [235] Milgrom 1983; [236] Bertone et al. 2005; [237] Bertone & Hooper 2018; [230] Planck Collaboration 2020; [228] Particle Data Group. *(Evidence B)*

#### U-15 Dark energy and cosmic tensions
* **Why it exists:** The expansion of the universe is observed to accelerate, and some measurements of its rate disagree.
* **How it is made (both halves):** Logic half: supernova evidence, the cosmological constant, independent probes, and the discrepancy between measurements of the expansion rate with proposed explanations. Intuition half: space-stretching pictures with caveats. Label what is measured and what is inferred.
* **What you can change:** Which probes, treatment of systematics, which explanation is explored.
* **How it is learned:** Modes M5, M6. Compare measurements side by side with their uncertainties and cite the latest reviews.
* **Bridge test:** Distinguishes measurements from interpretations and reports current status with dates.
* **Sources:** [231] Riess et al. 1998; [232] Perlmutter et al. 1999; [238] Di Valentino et al. 2021; [230] Planck Collaboration 2020. *(Evidence B)*

#### U-16 Astrophysics, black holes and gravitational waves
* **Why it exists:** Extreme objects test physics where gravity and matter are most intense.
* **How it is made (both halves):** Logic half: stellar structure and evolution, compact objects, accretion, gravitational-wave signals and detection. Intuition half: orbital pictures and the sound of a merger. Public data allow real analysis.
* **What you can change:** Object class, data source, model complexity.
* **How it is learned:** Modes M5, M6. Analyse open gravitational-wave data and compare with published results.
* **Bridge test:** Reproduces a published detection or parameter estimate with stated uncertainty.
* **Sources:** [213] Abbott et al. 2016; [239] Gravitational Wave Open Science Center; [212] Carroll General Relativity Notes; [206] NASA ADS. *(Evidence A)*

#### U-17 Observation, instruments and data pipelines
* **Why it exists:** All knowledge of the cosmos comes through instruments, and their systematics shape every conclusion.
* **How it is made (both halves):** Logic half: calibration, noise models, signal extraction, error propagation, archives and software tools. Intuition half: a feel for what a detector can and cannot see and how artefacts look.
* **What you can change:** Instrument model, calibration strategy, how systematics are tested.
* **How it is learned:** Modes M3, M5, M6. Process public telescope or detector data end to end and test with injected fake signals.
* **Bridge test:** Injected signals are recovered at the expected rate and artefacts are identified.
* **Sources:** [240] Astropy documentation; [239] GWOSC; [206] NASA ADS; [202] James et al.: Introduction to Statistical Learning. *(Evidence B)*

### Rung D Life

#### U-18 Chemistry and biochemistry
* **Why it exists:** Life is chemistry organised in space and time, and chemistry is quantum mechanics at a larger scale.
* **How it is made (both halves):** Logic half: bonding, energetics, kinetics, equilibrium, reaction mechanisms and computational chemistry. Intuition half: shapes, charges and flows of electrons as pictures of why molecules react. Hazards require qualified supervision and safety rules.
* **What you can change:** Level of quantum treatment, solvent and temperature, software used.
* **How it is learned:** Modes M5, M6. Predict reaction outcomes, then check with a computational chemistry toolkit and reference data.
* **Bridge test:** Predictions match reference data and safety limits are stated.
* **Sources:** [241] Chemistry LibreTexts; [242] IUPAC Gold Book; [243] RDKit documentation; [244] Alberts et al.: Molecular Biology of the Cell. *(Evidence A)*

#### U-19 Cell and molecular biology
* **Why it exists:** The cell is the unit of life, and DNA, RNA and proteins are its working parts.
* **How it is made (both halves):** Logic half: structure of DNA, the flow from DNA to RNA to protein, membranes, signalling, protein structure and function. Intuition half: the cell as a crowded, moving factory. Structure prediction now rivals experiments for many proteins.
* **What you can change:** Organism, scale, level of molecular detail.
* **How it is learned:** Modes M5, M6. Trace a gene to its protein and view structures in the open structure database.
* **Bridge test:** Explains a pathway from gene to function with correct molecular steps.
* **Sources:** [244] Molecular Biology of the Cell; [245] Crick 1970; [246] Watson & Crick 1953; [247] RCSB Protein Data Bank; [248] Jumper et al. 2021. *(Evidence A)*

#### U-20 Genetics, genomics and bioinformatics
* **Why it exists:** Heredity and sequence data link molecules to traits, disease and evolution.
* **How it is made (both halves):** Logic half: inheritance, variation, sequencing, alignment, statistics for genomes, and genome editing. Intuition half: the genome as a text with meaning in context. Privacy and ethics rules apply to human data.
* **What you can change:** Organism, data source, statistical threshold.
* **How it is learned:** Modes M5, M6. Analyse a public genome region with standard tools and compare with the database annotation.
* **Bridge test:** Matches database annotations and states uncertainty and ethical limits.
* **Sources:** [207] NCBI resources; [249] Biopython documentation; [250] Jinek et al. 2012; [244] Molecular Biology of the Cell. *(Evidence A)*

#### U-21 Evolution and ecology
* **Why it exists:** Evolution organises all of biology, and ecology explains how living things interact.
* **How it is made (both halves):** Logic half: selection, drift, population genetics, phylogenetic trees and ecosystem models. Intuition half: branching histories and webs of interaction. Fit models to data and compare alternatives.
* **What you can change:** Model class, time scale, assumptions about selection.
* **How it is learned:** Modes M5, M6. Build a tiny evolutionary simulation and compare it with real population data.
* **Bridge test:** Simulation behaviour matches theory and real data patterns are explained by named mechanisms.
* **Sources:** [251] Dobzhansky 1973; [244] Molecular Biology of the Cell; [207] NCBI resources; [252] Hardin 1968. *(Evidence A)*

#### U-22 Physiology and neuroscience
* **Why it exists:** Bodies and brains are control systems, and their principles shape behaviour and thought.
* **How it is made (both halves):** Logic half: membrane potentials and action-potential models, circuits, hormones, feedback and measurement methods. Intuition half: signals travelling through networks. Many questions about the brain remain open.
* **What you can change:** Scale (cell, circuit, brain), model detail.
* **How it is learned:** Modes M5, M6. Simulate a neuron model and relate it to measured signals.
* **Bridge test:** The model reproduces known spike behaviour and the agent states open questions in the field.
* **Sources:** [253] Hodgkin & Huxley 1952; [244] Molecular Biology of the Cell; [254] Kuhl 2004; [201] SciPy documentation. *(Evidence A)*

#### U-23 Origin of life and astrobiology
* **Why it exists:** How life began is unsolved, which makes it a model case for handling uncertainty.
* **How it is made (both halves):** Logic half: prebiotic chemistry experiments, RNA-world ideas, energy sources, planetary conditions and what would count as evidence. Intuition half: imagining pathways from chemistry to replication, each labelled speculative until tested.
* **What you can change:** Which hypotheses are explored, what evidence would change the view.
* **How it is learned:** Modes M5, M6. Build a table of hypotheses with the evidence for and against each.
* **Bridge test:** Separates tested findings from speculation and names the experiments that would discriminate.
* **Sources:** [255] Miller 1953; [256] Nurse 2008; [257] NASA Astrobiology; [195] Anderson 1972. *(Evidence C)*

#### U-24 Systems biology and what life is
* **Why it exists:** Life is more than parts: it is networks of interactions that sustain themselves.
* **How it is made (both halves):** Logic half: network models, feedback loops, stochastic dynamics, information flow in cells. Intuition half: life as organised processes rather than a list of ingredients. There is no single agreed definition of life.
* **What you can change:** Definition used, scale, level of simplification.
* **How it is learned:** Modes M5, M6. Simulate a small gene-regulation network and compare behaviours.
* **Bridge test:** Simulation shows the expected switches and oscillations, and the definitions of life are presented with their strengths and limits.
* **Sources:** [258] Kitano 2002; [256] Nurse 2008; [195] Anderson 1972; [248] Jumper et al. 2021. *(Evidence B)*

### Rung E Mind and society

#### U-25 Cognition, psychology and behaviour
* **Why it exists:** To communicate and to teach, an agent must model how people actually think and where they err.
* **How it is made (both halves):** Logic half: replicated findings, experimental design, heuristics and biases, theory of mind tasks. Intuition half: empathy and perspective. Weigh findings by replication.
* **What you can change:** Evidence required, population, theory versus data.
* **How it is learned:** Modes M5, M6. Read primary studies with replications and sort them.
* **Bridge test:** Separates replicated from unreplicated findings with sources.
* **Sources:** [259] Tversky & Kahneman 1974; [260] Kahneman & Tversky 1979; [199] Open Science Collaboration 2015; [261] Gigerenzer & Gaissmaier 2011; [106] Kahneman & Klein 2009; [262] Premack & Woodruff 1978; [263] Kosinski 2023. *(Evidence B)*

#### U-26 Social systems, economics and institutions
* **Why it exists:** Groups behave differently from individuals, and incentives shape outcomes.
* **How it is made (both halves):** Logic half: networks, game theory, models of segregation, commons problems and information asymmetry. Intuition half: seeing how local rules produce large patterns. Test models against data.
* **What you can change:** Network structure, incentive design, population size.
* **How it is learned:** Modes M5, M6. Re-implement classic models and compare with real cases.
* **Bridge test:** Reproduces classic results and explains which assumption drives them.
* **Sources:** [264] Granovetter 1973; [265] Schelling 1971; [252] Hardin 1968; [266] Akerlof 1970; [267] Park et al. 2023. *(Evidence B)*

#### U-27 Philosophy of science, mind and knowledge
* **Why it exists:** It tests what counts as knowledge and explanation and keeps open questions honest.
* **How it is made (both halves):** Logic half: epistemology, falsification, paradigm shifts, explanation and models, formal argument analysis. Intuition half: thought experiments and the unresolved problem of consciousness. Ethics of AI guards against harm.
* **What you can change:** Philosophical framework, burden of proof.
* **How it is learned:** Modes M5. Map arguments in contested debates and identify cruxes.
* **Bridge test:** Presents each side's strongest case and names the crux without taking a hidden stance.
* **Sources:** [268] SEP: Epistemology; [198] SEP: Karl Popper; [269] SEP: Thomas Kuhn; [270] SEP: Imre Lakatos; [271] SEP: Consciousness; [272] SEP: Scientific Explanation; [273] SEP: Ethics of Artificial Intelligence and Robotics. *(Evidence A)*

#### U-28 Language and linguistics
* **Why it exists:** Language is the medium of nearly all human knowledge.
* **How it is made (both halves):** Logic half: phonology, morphology, syntax, semantics, pragmatics, information theory and statistical models of language. Intuition half: feeling for register, implication and style. Meaning is not the same as form.
* **What you can change:** Level of analysis, language family, corpus.
* **How it is learned:** Modes M1, M5, M6. Analyse texts across languages with typological data and corpora.
* **Bridge test:** Correct analysis of structure and implied meaning across several languages.
* **Sources:** [274] Jurafsky & Martin: Speech and Language Processing; [275] World Atlas of Language Structures Online; [254] Kuhl 2004; [276] SEP: Pragmatics; [277] Bender & Koller 2020; [278] Shannon 1948. *(Evidence B)*

### Rung F Communication and learning

#### U-29 Learning any human language
* **Why it exists:** Language learning unlocks people and knowledge, and it follows reliable principles.
* **How it is made (both halves):** Logic half: structured input, vocabulary frequency, grammar patterns, spaced repetition and retrieval practice, milestones on a common scale. Intuition half: immersion in meaning, rhythm and culture. Use translation as a test, not the only method.
* **What you can change:** Daily time, input versus output, spacing schedule, target level.
* **How it is learned:** Modes M5, M6. Learn one language with a fixed plan, track vocabulary retention and level checks.
* **Bridge test:** Passes a level test and communicates in real conversation, with retention above target.
* **Sources:** [279] Dunlosky et al. 2013; [280] Cepeda et al. 2006; [281] Roediger & Karpicke 2006; [282] Common European Framework of Reference for Languages; [283] Anki Manual; [275] WALS Online; [274] Jurafsky & Martin. *(Evidence B)*

#### U-30 Learning any skill or field fast
* **Why it exists:** The agent must master new fields on demand.
* **How it is made (both halves):** Logic half: map the territory, learn the core ideas, move from textbook to papers, practise deliberately with feedback, test recall, and teach back. Intuition half: finding the analogy that makes the field feel familiar. One-to-one tutoring and good practice raise results strongly.
* **What you can change:** Time per stage, practice difficulty, feedback source.
* **How it is learned:** Modes M5, M6. Learn a new field in 30 days with a plan, tests and a written explanation.
* **Bridge test:** Passes a competence test and writes an explanation an expert endorses.
* **Sources:** [100] Ericsson et al. 1993; [279] Dunlosky et al. 2013; [284] Bloom 1984; [101] Chi et al. 1989; [281] Roediger & Karpicke 2006; [102] Pan & Yang 2010. *(Evidence B)*

#### U-31 Explaining anything at any level
* **Why it exists:** Understanding is proved by explaining it clearly to different people.
* **How it is made (both halves):** Logic half: structure the explanation from prerequisites to result, with correct definitions. Intuition half: choose an analogy and example for this audience and state where the analogy fails. Test by asking the listener to explain it back.
* **What you can change:** Audience model, depth, analogy choice.
* **How it is learned:** Modes M5. Explain ten topics at three levels and test comprehension.
* **Bridge test:** Listeners at each level can restate the idea and a specialist finds no errors.
* **Sources:** [101] Chi et al. 1989; [115] Gentner 1983; [285] Zheng et al. 2024; [276] SEP: Pragmatics. *(Evidence B)*

#### U-32 Translation and cross-cultural communication
* **Why it exists:** Meaning must survive between languages and cultures.
* **How it is made (both halves):** Logic half: structure, glossaries, back-translation and quality metrics. Intuition half: register, tone and effect. State what is preserved and what changes.
* **What you can change:** Preserved features, register, review panel.
* **How it is learned:** Modes M1, M2, M5. Translate with explicit preservation lists and compare with native review.
* **Bridge test:** Native review finds no meaning-changing error.
* **Sources:** [286] NLLB Team 2022; [287] Rei et al. 2020; [274] Jurafsky & Martin; [276] SEP: Pragmatics; [288] Unicode Standard. *(Evidence B)*

#### U-33 Writing and presenting science
* **Why it exists:** Findings matter only if readers can follow, check and reuse them.
* **How it is made (both halves):** Logic half: structure, exact methods, honest uncertainty, reporting guidelines, reproducible figures. Intuition half: a clear story and strong visuals.
* **What you can change:** Audience, length, figure style.
* **How it is learned:** Modes M5, M6. Write short papers and posters from public data and review them against reporting guidelines.
* **Bridge test:** A cold reader can reproduce the main result from the text and figures.
* **Sources:** [289] Federal Plain Language Guidelines; [290] EQUATOR Network; [156] Wilke: Fundamentals of Data Visualization; [291] Google developer documentation style guide. *(Evidence A)*

#### U-34 Critical dialogue and disagreement
* **Why it exists:** Good conversation finds truth and prevents needless conflict.
* **How it is made (both halves):** Logic half: identify the crux, separate facts from values, check arguments for fallacies. Intuition half: listening for what the other person needs and stating their view so they agree it is fair. People reason better in group discussion than alone.
* **What you can change:** Strength of challenge, tone, how often to summarise.
* **How it is learned:** Modes M5, M7. Practise steelmanning and crux-finding on contested topics with a reviewer.
* **Bridge test:** The other side agrees the summary of their position is fair, and the crux is named.
* **Sources:** [292] Mercier & Sperber 2011; [26] Du et al. 2023; [293] SEP: Classical Logic; [294] SEP: Fallacies. *(Evidence B)*

### Rung G Frontier and control

#### U-35 Handling open problems and unknowns
* **Why it exists:** Frontier topics invite hype, false certainty and pseudoscience.
* **How it is made (both halves):** Logic half: label every statement as established, supported, speculative or unknown; ask what evidence would change the view; re-check current literature before stating frontier claims. Intuition half: staying curious about alternatives without endorsing them.
* **What you can change:** Evidence thresholds, how often claims are refreshed.
* **How it is learned:** Modes M5, M6. Write status reports on five open problems with dated sources.
* **Bridge test:** No open problem is presented as solved and each status report is dated and sourced.
* **Sources:** [295] SEP: Science and Pseudo-Science; [198] SEP: Karl Popper; [269] SEP: Thomas Kuhn; [270] SEP: Imre Lakatos; [200] Ioannidis 2005. *(Evidence B)*

#### U-36 Mode arbitration and calibrated confidence
* **Why it exists:** Using the wrong engine, intuition or computation, is the most common failure.
* **How it is made (both halves):** Logic half: stated probabilities, scoring and checks. Intuition half: fast judgement where the domain has regularities and past feedback. Choose by asking whether the answer can be checked, how stable the domain is, and how costly an error would be.
* **What you can change:** Thresholds, scoring rule, how confidence is shown.
* **How it is learned:** Modes M5, M7. Log mode choices and confidences with outcomes and tune.
* **Bridge test:** Stated confidence matches observed frequency, and mode choices beat fixed-mode baselines.
* **Sources:** [106] Kahneman & Klein 2009; [186] Evans & Stanovich 2013; [296] Kadavath et al. 2022; [297] Lin et al. 2022; [188] Snell et al. 2024; [187] SEP: Bayes' Theorem. *(Evidence B)*

## Part IV: Revenue Layer: master-level income skills

The Revenue Layer gives all three agents the business skills to turn checked work into lawful income: find real demand, make an honest offer, win customers, deliver with quality gates, get paid and stay compliant, then measure and protect. It does not guarantee income: most online ventures earn little or nothing, platforms restrict some automation, and legal and tax rules depend on the country (United States sources are used as examples).

Every stage obeys R-16: no payment, contract, new account, public post or message to a new person without human approval, with spending caps, audit logs and a named accountable human.

### The tree (Pipeline of 5 stages)

* **Stage 1 Find (R-01 to R-04):** Market and customer discovery; Offer design and positioning; Pricing and unit economics; Opportunity screening and kill criteria.
* **Stage 2 Win (R-05 to R-08):** Outreach and communication; Sales conversation and negotiation; Proposals, contracts and scope control; Channels and platforms.
* **Stage 3 Deliver (R-09 to R-11):** Delivery system and quality gates; Customer support and expectation management; Productised and automated service design.
* **Stage 4 Get paid (R-12 to R-13):** Billing, payments and accounting basics; Legal, platform terms and compliance.
* **Stage 5 Grow and protect (R-14 to R-16):** Metrics and experiments; Risk, fraud and ethics; Autonomy governance for money-making agents.

---

### Stage 1 Find

#### R-01 Market and customer discovery
* **Why it matters:** Most ventures fail by building what nobody pays for. Demand has to be found before work is built.
* **How it works:** Logic half: define a narrow customer and the job they need done, then count evidence of paid demand (existing spending, workarounds, repeated requests). Imagination half: notice unmet needs and listen for the problem behind the stated request. Speak with 10 to 20 real prospects or read public demand signals before building anything.
* **What you can change:** Narrowness of the segment, number of conversations, what counts as evidence (money or commitment, not compliments).
* **How it is learned:** Modes M5, M6. Run discovery on three niches and score the evidence in a log.
* **Proof it works:** A niche where several prospects describe the problem unprompted and at least one will pay or commit. Guardrail: be honest about who you are and how data is used.
* **Sources:** [298] Y Combinator Startup School; [299] Y Combinator Library; [266] Akerlof 1970; [165] Kohavi et al. 2009. *(Evidence C)*

#### R-02 Offer design and positioning
* **Why it matters:** People pay for a clear result, not for skills. A sharp offer is easier to sell and to deliver.
* **How it works:** State who it is for, the result, what is included and excluded, the price, the proof, and the alternative the customer would otherwise use. Package a repeatable service with a fixed scope so delivery can be checked.
* **What you can change:** Scope size, packaging, guarantee, proof type.
* **How it is learned:** Modes M5, M6. Write ten offers and test whether strangers can restate them correctly in one sentence.
* **Proof it works:** Prospects restate the offer accurately and can tell why it differs from alternatives. Guardrail: no claim the work cannot deliver.
* **Sources:** [298] Startup School; [299] Y Combinator Library; [300] Stripe Atlas guides; [122] Design Council: The Double Diamond. *(Evidence C)*

#### R-03 Pricing and unit economics
* **Why it matters:** A sale that loses money is not income. Price decides whether the business can continue.
* **How it works:** Add all costs (time, tools, compute, fees, taxes), set a target margin, and compare with what customers pay for alternatives. People judge prices against anchors and mental accounts, so state value and options clearly and honestly.
* **What you can change:** Pricing model (fixed, hourly, subscription), tiers, discount policy.
* **How it is learned:** Modes M5, M6. Build a cost model for three offers and run honest price tests with small groups.
* **Proof it works:** A model showing margin per sale under realistic costs and a tested price. Guardrail: no fake scarcity or hidden fees.
* **Sources:** [301] Thaler 1985; [259] Tversky & Kahneman 1974; [302] Damodaran valuation resources; [300] Stripe Atlas guides. *(Evidence B)*

#### R-04 Opportunity screening and kill criteria
* **Why it matters:** Time is the scarce resource. Small bets with predefined limits beat open-ended projects, and scams are common.
* **How it works:** Estimate probability, payoff and cost for each opportunity, run the cheapest test first, and set stop rules in advance. Treat guaranteed returns, upfront fees, secrecy and pressure as warning signs.
* **What you can change:** Loss limit, test length, stop rule.
* **How it is learned:** Modes M5, M7. Keep an opportunity log with predicted and actual results.
* **Proof it works:** Bets are stopped at their predefined limits and warning signs are flagged before any payment. Guardrail: never pay to access 'guaranteed' income.
* **Sources:** [303] SEP: Decision Theory; [203] Downey: Think Bayes 2; [298] Startup School; [299] Y Combinator Library. *(Evidence B)*

---

### Stage 2 Win

#### R-05 Outreach and communication
* **Why it matters:** Customers must hear of an offer, and trust is lost by spam or deception.
* **How it works:** Write short, specific, relevant messages to people who have a reason to care; identify yourself, state value and make it easy to decline. In the United States commercial email must follow the CAN-SPAM rules (accurate headers, clear identification, working opt-out); the EU adds privacy rules such as GDPR.
* **What you can change:** Audience, channel, message length, follow-up number.
* **How it is learned:** Modes M5, M6. Draft messages, have them reviewed for honesty and rule compliance, and track replies.
* **Proof it works:** Replies and opt-outs are handled correctly and every message passes the rules checklist. Guardrail: no scraping of private data, no fake identities.
* **Sources:** [304] FTC CAN-SPAM Act Guide; [305] EU GDPR; [163] FTC advertising guidance; [289] Federal Plain Language Guidelines. *(Evidence B)*

#### R-06 Sales conversation and negotiation
* **Why it matters:** Conversation turns interest into agreement, and honest negotiation protects both sides.
* **How it works:** Listen for the real need, qualify fit, state value in the customer's terms, answer objections truthfully, and agree scope and price in writing. First numbers act as anchors, so prepare your own and do not accept an anchor unexamined.
* **What you can change:** Opening position, concessions, walk-away point.
* **How it is learned:** Modes M5. Practise on recorded scenarios with a reviewer scoring honesty and clarity.
* **Proof it works:** Agreements are clear and both sides can restate them. Guardrail: never misrepresent capability or results.
* **Sources:** [306] Galinsky & Mussweiler 2001; [259] Tversky & Kahneman 1974; [292] Mercier & Sperber 2011; [298] Startup School. *(Evidence B)*

#### R-07 Proposals, contracts and scope control
* **Why it matters:** Most disputes come from unclear scope, payment terms or ownership.
* **How it works:** Write down deliverables, acceptance criteria, timeline, price, payment terms, change requests, ownership and liability. Use professionally reviewed templates. Copyright rules for AI-assisted work differ from ordinary work, so state who owns what.
* **What you can change:** Level of detail, milestone structure, ownership terms.
* **How it is learned:** Modes M5, M6. Draft contracts for sample projects and have a qualified person review them. This is not legal advice.
* **Proof it works:** A reviewer finds no ambiguity in scope, payment or ownership. Guardrail: qualified legal review for anything binding.
* **Sources:** [300] Stripe Atlas guides; [149] US Copyright Office: Copyright and AI; [183] Creative Commons licences; [299] Y Combinator Library. *(Evidence A)*

#### R-08 Channels and platforms
* **Why it matters:** Where an offer is placed decides who sees it, and every platform has its own rules.
* **How it works:** Try a few channels cheaply: marketplaces, app stores, communities, search-friendly content, direct outreach. Read each platform's terms before use; many restrict automation, fake accounts and certain content. App stores enforce developer policies.
* **What you can change:** Channel mix, budget per channel, content format.
* **How it is learned:** Modes M5, M6. Test three channels with small budgets and record cost per lead.
* **Proof it works:** At least one channel gives leads at an acceptable cost with no policy violations. Guardrail: follow the terms of every platform.
* **Sources:** [307] Google Play Developer Policy Center; [166] Google SEO Starter Guide; [299] Y Combinator Library; [163] FTC advertising guidance. *(Evidence C)*

### Stage 3 Deliver

#### R-09 Delivery system and quality gates
* **Why it matters:** Reputation and repeat income depend on checked, on-time delivery.
* **How it works:** Use the skills of Agents 1 to 3 inside a fixed pipeline: written acceptance criteria, automated checks for code, proofreading and source verification for text, visual review for graphics, then a human check before anything is sent.
* **What you can change:** Gate list, review depth, turnaround target.
* **How it is learned:** Modes M5, M6. Run three pilot deliveries and log every defect found at each gate.
* **Proof it works:** Defects found by the customer fall to near zero across pilots. Guardrail: nothing leaves without the final gate.
* **Sources:** [69] Software Engineering at Google; [39] Site Reliability Engineering; [308] Dhuliawala et al. 2023; [309] Min et al. 2023. *(Evidence B)*

#### R-10 Customer support and expectation management
* **Why it matters:** Clear communication after the sale prevents refunds and disputes.
* **How it works:** Confirm scope at the start, give regular status updates, answer quickly, handle problems openly, and have written policies for revisions, refunds and escalation to a human.
* **What you can change:** Response time, revision allowance, refund policy.
* **How it is learned:** Modes M5. Role-play support cases and review tone and accuracy.
* **Proof it works:** Customers can state what to expect and when. Guardrail: escalate disputes and legal threats to a human.
* **Sources:** [289] Federal Plain Language Guidelines; [298] Startup School; [299] Y Combinator Library; [39] Site Reliability Engineering. *(Evidence C)*

#### R-11 Productised and automated service design
* **Why it matters:** Automation raises income per hour only if failures are controlled.
* **How it works:** Split the service into steps, automate the repeatable ones, keep human approval where mistakes are costly, monitor outputs, and plan for failure. Prefer simple loops over complex autonomy.
* **What you can change:** Which steps are automated, approval points, monitoring.
* **How it is learned:** Modes M5, M6. Automate one step at a time and compare error rate and cost with the manual version.
* **Proof it works:** Error rate and time per job improve with no loss of quality. Guardrail: human approval for money, contracts and public statements.
* **Sources:** [105] Anthropic 2024; [18] Yao et al. 2023; [39] Site Reliability Engineering; [79] OWASP Top 10 for LLMs; [40] Amodei et al. 2016. *(Evidence C)*

### Stage 4 Get paid

#### R-12 Billing, payments and accounting basics
* **Why it matters:** Revenue counts only when it is collected, recorded and reported correctly.
* **How it works:** Invoice clearly, use a regulated payment processor, keep records of every transaction, reconcile accounts, and set money aside for taxes. In the United States self-employment income is generally taxable and may need estimated payments; verify details with official guidance and a qualified accountant.
* **What you can change:** Processor, invoicing cadence, bookkeeping tool.
* **How it is learned:** Modes M5, M6. Set up a practice ledger, issue sample invoices, and reconcile them.
* **Proof it works:** Records match bank statements to the cent. Guardrail: never hold or move money without human authorisation.
* **Sources:** [310] Stripe documentation; [300] Stripe Atlas guides; [311] IRS Publication 334. *(Evidence A)*

#### R-13 Legal, platform terms and compliance
* **Why it matters:** Legal and policy mistakes can end a business or an account.
* **How it works:** Know the basics of contracts, intellectual property, privacy, advertising disclosure and consumer protection; read the terms of cloud services, APIs and marketplaces, which may limit automation, scraping, resale and account creation; disclose AI use where required. Rules vary by country and change.
* **What you can change:** Jurisdiction, data handled, which terms apply.
* **How it is learned:** Modes M5, M6. Create a compliance checklist for each service and review it against current official texts.
* **Proof it works:** Each service has a dated checklist of applicable rules and terms. Guardrail: this is education, not legal advice.
* **Sources:** [312] Google Cloud Terms of Service; [307] Google Play Developer Policy Center; [305] EU GDPR; [163] FTC advertising guidance; [149] US Copyright Office. *(Evidence A)*

### Stage 5 Grow and protect

#### R-14 Metrics and experiments
* **Why it matters:** Improvement needs measurement that is not fooled by noise.
* **How it works:** Track the funnel (visits, enquiries, sales, delivery, repeat), cost to acquire, margin and retention. Test one change at a time with pre-stated success criteria and enough samples, and report null results.
* **What you can change:** Metric set, sample size, test length.
* **How it is learned:** Modes M5, M7. Run small experiments on offers and messages and record pre-stated criteria.
* **Proof it works:** Decisions follow results that exceed noise. Guardrail: no cherry-picking or fake testimonials.
* **Sources:** [165] Kohavi et al. 2009; [200] Ioannidis 2005; [203] Downey: Think Bayes 2; [202] James et al. *(Evidence B)*

#### R-15 Risk, fraud and ethics
* **Why it matters:** Short-term gains from deception destroy trust and invite penalties.
* **How it works:** Identify risks: payment fraud, chargebacks, scams, privacy breaches, misleading design. Refuse deceptive tactics, protect customer data, and review decisions against harms to customers and third parties.
* **What you can change:** Risk register, thresholds for refusal, review frequency.
* **How it is learned:** Modes M5. Review case studies of deceptive practices and write the honest alternative.
* **Proof it works:** No deceptive design or claim passes review. Guardrail: refuse any task that requires deception or harm.
* **Sources:** [164] FTC 2022; [40] Amodei et al. 2016; [273] SEP: Ethics of AI and Robotics; [313] NIST AI Risk Management Framework. *(Evidence B)*

#### R-16 Autonomy governance for money-making agents
* **Why it matters:** An agent that can spend, sign, post or message can also do harm quickly. Limits must be set before autonomy.
* **How it works:** Define what the agent may do alone and what needs human approval: payments, contracts, new accounts, public posts, messages to new people, deletions. Use least-privilege credentials, spending caps, a kill switch and an audit log. Treat web content and files as untrusted, since hidden instructions can hijack an agent.
* **What you can change:** Approval list, caps, credential scope, audit detail.
* **How it is learned:** Modes M5, M7. Test the agent against seeded injection and overspending scenarios and tune the gates.
* **Proof it works:** No unapproved payment, post or contract in testing, and every action is logged. Guardrail: a named human remains accountable for the agent.
* **Sources:** [79] OWASP Top 10 for LLMs; [80] Greshake et al. 2023; [313] NIST AI Risk Management Framework; [105] Anthropic 2024; [40] Amodei et al. 2016. *(Evidence B)*

## Appendix B: Housing the trees in an ICM workspace

Jake Van Clief's Interpretable Context Methodology organises an agent's work as folders and plain-text files: five layers (0 root file, 1 routing file, 2 stage contract, 3 reference material, 4 working artifacts), numbered stage folders, stage contracts with Inputs, Process and Outputs, one-way references and one canonical home per fact. [15] Van Clief 2026; [103] Interpretable-Context-Methodology reference implementation; [104] ICM core conventions.

The layout below is a proposed mapping onto those layers. It is a design suggestion built from the published conventions, not a layout taken from the repository. Files stay short (the project's checklist asks for stage files under 80 lines and references under 200), so an agent loads one skill card at a time instead of this whole document.

```text
skills-workspace/
├── CONFIG.md            # L0 root file (always loaded)
├── CONTEXT.md           # L1 routing: which agent, tier, ring, rung or stage
├── _config/
│   └── shared/
│       ├── bibliography.md # L3 one canonical list of sources
│       └── rules.md        # L3 safety rules, approval list (R-16), evidence grades, modes M1-M8
└── agents/
    ├── 1-code/
    │   ├── tier-0-ground/
    │   │   └── L-01-reading/
    │   │       ├── CONTEXT.md       # L2 stage contract: Inputs, Process, Outputs
    │   │       ├── references/      # L3 the skill card
    │   │       └── output/          # L4 practice results and logged lessons
    │   └── ...
    ├── 2-graphics/
    ├── 3-understanding/
    └── revenue/
```

### How one skill runs

* **01-practice:** generates tasks from the card's learning protocol.
* **02-verify-or-judge:** applies a checker for logic skills and a blind judge or panel for imagination skills.
* **03-reflect:** writes what failed and why.
* **04-store-lesson:** writes a short lesson file into that skill's output folder and, only after verification, into the reference layer. 

Known limits of ICM (real-time multi-agent loops, high concurrency, complex automated branching) apply, as stated in the repository.
